# P2.2e 精确检索实验室实施基线

状态：设计候选；开始业务实现前必须获得维护者批准。

## 1. 目标结果

P2.2e 只闭合一个边界清晰的工作流：

```text
发布不可变检索策略
  -> 鉴权精确 READY 索引版本与策略版本
  -> 准入并核算查询 Embedding
  -> 执行一条工作区限定的精确余弦查询
  -> 应用确定性的重叠与上下文预算规则
  -> 披露有界且当前获授权的证据
  -> 返回 MATCHES 或类型化 NO_EVIDENCE
```

本切片证明检索机制与治理闭环，不会上线 Knowledge 产品页面，不生成答案，不绑定
Application 草稿，也不创建生产 Run。

## 2. 权威依据与变更分类

本基线在不改变不变量、模块边界、技术基线、发布语义、安全策略或公开契约的情况下，
落实 ADR-0006 和已批准的 P2.2 计划，因此不需要新 ADR。

- 阶段：P2，切片 P2.2e。
- 所属模块：`knowledge`。
- 允许的同步依赖：`identity`、`capability-registry`、`governance`。
- 禁止的依赖：`application`、`release`、`runtime` 及其他模块内部实现。
- 有状态依赖：仅使用现有 PostgreSQL 18 与 pgvector。
- 公开契约：现有 `RetrievalPolicyVersion`、`CreateRetrievalPolicyVersionRequest`、
  `KnowledgeRetrievalTestRequest`、`KnowledgeRetrievalResult` 和
  `KnowledgeRetrievalHit`。
- 迁移需求：无。P2.2b 已建立所需的不可变策略与索引表。
- 前端与国际化键：本切片没有；页面在 P2.4 前仍不上线。
- 文档：英文源文档与等价简体中文证据必须同时存在。

如果实现需要新增表、ANN 索引、队列、可部署单元、框架、公开 API 中的提供商类型，
或修改公开契约，必须停止本切片，并先完成受保护变更审查。

## 3. 现有资产与缺口

已经具备：

- `retrieval_policy_version` 不可变持久化与仅插入触发器；
- READY 不可变索引版本、精确固定的 Embedding 路由配置与 pgvector 条目；
- 提供商无关的 Embedding 执行以及 Governance 预留/组件契约；
- 工作区与主体作用域解析；
- 标记为 `contract-only` 的 OpenAPI 3.1 检索策略和检索实验室契约；
- 载荷保留与敏感字段遮蔽的保留策略标志。

仍需实现：

- Knowledge 公共检索边界与不可变策略目录；
- 发布校验与规范策略摘要；
- 受治理的查询 Embedding 编排；
- 一条精确且限定作用域的排序仓储语句；
- 确定性的排序后策略应用；
- 有界披露、遮蔽、遥测、审计和 REST 适配器；
- 隔离、历史、保留、失败与契约证据。

数据库对 `maximum_context_input_units` 的约束有意宽于公开 OpenAPI。实现必须执行公开
`maxContextTokens` 的 `128..200000` 范围；宽松的存储约束不代表可以放宽 API。

当前 Governance 目录在工作区尚无保留策略数据行时，会返回版本 `0` 的有效默认策略，
但已批准的策略来源契约要求持久版本至少为 `1`。因此 P2.2e 需要一个向后兼容的
Governance 公共操作：数据行不存在时，原子落地现有默认值为版本 `1`；已存在时返回
当前持久版本。Knowledge 不得写 Governance 表，也不得自行伪造版本号。

## 4. 公共模块边界

`io.apvero.platform.knowledge` 包提供与下列结构等价的提供商无关记录和接口：

```text
RetrievalPolicyVersionCatalog
  publish(workspaceId, commandContext, request) -> RetrievalPolicyVersion
  list(workspaceId) -> List<RetrievalPolicyVersion>

KnowledgeRetrieval
  retrieve(workspaceId, principal, indexVersionId, policyVersionId, query)
    -> KnowledgeRetrievalResult
```

结果包含精确索引版本和策略版本 ID、SHA-256 查询摘要、`MATCHES` 或
`NO_EVIDENCE`、有序命中项与耗时毫秒数。命中项只包含契约规定的不可变血缘、
规范化分数、内容摘要、可选有界内容和获授权定位锚点。

公共边界不得暴露 Spring AI、pgvector、jOOQ、提供商 SDK、数据库记录、Secret
Reference、原始提供商响应、文件系统路径、对象存储键或无限制源 URL 类型。

## 5. 不可变检索策略发布

### 5.1 调用方可控制字段

- slug 与语义版本；
- `topK`：`1..100`；
- `maxContextTokens`：`128..200000`；
- `minimumScore`：`[0,1]`，且必须是有限值；
- 重叠处理：`KEEP` 或 `COLLAPSE_ADJACENT`。

### 5.2 平台控制字段

- `retrievalAlgorithmVersion = exact-cosine@1.0.0`；
- `tokenEstimatorVersion` 使用已经冻结的确定性估算器；
- 发布时工作区当前 Retention Policy 版本，仅作为来源证明；
- `emptyEvidenceBehavior = NO_EVIDENCE`；
- 规范策略摘要、创建者和 UTC 创建时间。

规范摘要按固定顺序对带长度前缀的 UTF-8 字段值计算 SHA-256。数值采用与区域设置无关
的规范十进制文本。摘要包含所有影响行为的字段和平台分配字段，但不包含生成 ID、
操作者和创建时间。

发布语义：

- 同一工作区、slug、版本和摘要完全相同，返回已有版本；
- slug/版本被不同内容复用，返回稳定冲突；
- 相同摘要以另一 slug/版本发布，依据现有唯一约束返回稳定的重复策略冲突；
- 读写始终限定 tenant/workspace；
- 普通 API 永远不能更新或删除已发布行。

策略发布产生一条管理审计事件，只包含身份和摘要，不包含内容或密钥。

构建摘要前，Knowledge 通过 Governance 公共 API 获得当前持久 Retention Policy。
并发首次发布必须收敛到同一个默认版本 `1`，不得生成重复行、返回版本 `0`，也不得让
Knowledge 访问 Governance 存储。

## 6. 检索执行顺序

单次请求按以下顺序失败关闭：

1. Knowledge 被禁用时拒绝请求；
2. 解析已认证主体和工作区作用域；
3. 仅裁剪边界空白；空查询或超过 20,000 个 Unicode 码点时拒绝；其余查询字节保持
   不变并用于 Embedding；
4. 对规范化 UTF-8 查询字节计算 `sha256:`；永不记录原始查询；
5. 在同一工作区加载精确 READY 索引版本和精确策略版本；
6. 解析索引版本固定的 READY Embedding 路由，并校验其不可变配置和向量维度；
7. 通过 `capability-registry` 获取估算用量；
8. 在调用前建立 `KNOWLEDGE_QUERY / EMBEDDING_QUERY` Governance 预留与组件；
9. 在没有开放数据库事务的情况下执行一次有界查询 Embedding 调用；
10. 校验只返回一个向量、维度精确、元素有限且范数非零；
11. 使用请求级幂等身份，只结算一次实际或估算用量；
12. 执行精确作用域排序语句；
13. 按确定性排名顺序应用重叠与上下文预算；
14. 通过 Governance 读取当前有效 Retention Policy，并在响应投影时应用载荷抑制与
    遮蔽规则；
15. 至少保留一个命中时返回 `MATCHES`，否则成功返回 `NO_EVIDENCE`；
16. 记录安全遥测并结束 Trace。

准入拒绝必须发生在提供商调用前。已知结果的提供商失败按失败结算。付费结果不明确时
不得盲目重试，返回现有稳定的“需要对账”错误族。

检索实验室请求为同步请求，不新增 Knowledge 查询持久化表。Governance 记录是持久的
计费证据；本次实验操作的检索证据由响应与 Trace 承载。

## 7. 精确排序内核

仓储通过一条 SQL，从请求的 READY 索引版本经其 Build 连接到 Entry 与不可变 Chunk
血缘。下列条件必须在同一语句内、排序和限制之前生效：

- tenant ID；
- workspace ID；
- 精确索引版本 ID；
- `READY` 版本状态；
- Build 与 Entry 复合作用域；
- 查询向量维度等于已发布版本维度；
- 余弦相似度不低于不可变策略阈值。

排序规则：

```text
余弦距离升序
  -> 不可变 chunk UUID 升序
```

数据库距离是排序依据。对外分数为
`clamp(1 - cosine_distance, 0, 1)`。Java 不得重新按浮点分数排序，不得全局检索候选
后再过滤工作区。

SQL 限制精确等于 `topK`。P2.2e 不增加隐藏的超额召回或回填。当前 Source tombstone
状态有意不参与条件：旧的已发布索引版本仍可检索。当前鉴权和披露策略仍在读取时执行。

## 8. 确定性的排序后规则

### 8.1 重叠

`KEEP` 保留 SQL 顺序。

`COLLAPSE_ADJACENT` 只将候选与同一不可变 Document 中已接受的命中比较。两个 Chunk
的已存字符范围相交时视为重叠；缺少范围元数据时不得猜测重叠。排名更靠前者保留；
距离相同时已经由 chunk UUID 决定顺序。

丢弃命中后，不从 SQL `topK` 之外补充。

### 8.2 上下文预算

固定的估算器对实际允许披露的内容计算单位。按排名顺序处理已接受命中：

- 只有完整有界内容能放入剩余预算时才纳入；
- 不得通过静默截断内容制造“可放入”结果；
- 过大的命中被跳过，后续较小命中仍可参与，但不得改变其相对顺序；
- 仅元数据命中消耗零内容单位，但仍受 `topK` 限制；
- 过滤后的响应 rank 重新连续编号。

上述算法属于 `exact-cosine@1.0.0`。改变算法必须发布新算法版本，不能静默修改代码。

### 8.3 空证据

阈值过滤、重叠折叠、上下文限制或当前披露策略都可能导致零命中。这是命中数组为空的
成功 `NO_EVIDENCE`，不是异常，更不允许回退为无依据回答。

## 9. 披露与保留

响应只允许暴露：

- 公共血缘 ID；
- rank、规范化分数和内容摘要；
- 当前策略允许保留载荷时，每个命中最多 20,000 字符的有界内容；
- 有界源标题/类型以及页码、标题、段落和行锚点。

`retainPayloads=false` 时内容为 `null`，血缘与摘要保留。`maskSensitiveFields=true`
时，在响应投影和任何观测导出前执行 Governance 的披露决定。当前平台没有已批准的
非结构化文本遮蔽器，因此 P2.2e 在该标志启用时失败关闭并抑制内容。它不得在
Knowledge 内另造一套遮蔽词表，也不得把几个正则表达式包装成企业 DLP。未来的共享
遮蔽器必须单独审查其行为和测试。

响应永不暴露快照字节、契约外内部表键、本地/对象路径、Secret Reference、提供商
消息、提供商请求 ID、原始源 URL 或跨工作区存在性提示。无权限或不同作用域资源使用
现有不可区分的作用域内 not-found 行为。

## 10. 错误、审计与遥测

稳定错误包括：能力禁用、请求无效、作用域资源不存在、索引版本非 READY、路由无效或
不可用、准入拒绝、查询过大、提供商失败、结果不明确、向量无效、维度不匹配和结算
冲突。后端消息仍是稳定代码加安全参数，由客户端负责本地化。

策略发布产生管理审计。高频检索测试不制造管理审计噪声，而是产生类型化 Trace/操作
证据以及 Governance 台账记录。

低基数指标：

- 检索请求数与结果；
- 端到端及提供商延迟；
- 排序命中数与返回命中数；
- 粗粒度分数桶；
- `NO_EVIDENCE` 数；
- 准入、提供商、校验和结算失败族。

tenant/workspace ID、查询或内容、Route/Index/Policy ID、URL 和提供商请求 ID 禁止
作为指标标签。普通日志禁止包含原始查询和返回内容。

## 11. 实施检查点

### P2.2e-1 — 策略发布

- 公共策略记录、目录与 REST 适配器；
- 严格校验、平台分配字段与规范摘要；
- 向后兼容的 Governance 操作，在不跨模块访问数据库的情况下落地/返回持久
  Retention Policy 版本；
- 作用域幂等/冲突行为、审计与仓储测试。

### P2.2e-2 — 精确检索内核

- 公共检索结果/命中边界；
- 一条作用域限定的 pgvector 余弦语句与有界投影；
- 确定性分数、平局、阈值和 tombstone 历史行为；
- Testcontainers 隔离与查询计划证据。

### P2.2e-3 — 受治理查询执行

- 固定路由解析、报价、预留、调用与结算；
- 向量校验、失败规范化与禁止盲目重试；
- 本地确定性适配器与协议桩测试。

### P2.2e-4 — 策略应用与披露

- 重叠折叠、估算器预算与类型化 `NO_EVIDENCE`；
- 当前保留策略、遮蔽或抑制、安全定位器策略与 REST 一致性；
- 英文、简体中文、混合 Unicode 和边界输入的单元/性质测试。

### P2.2e-5 — 切片验证候选

- 架构、Java、Testcontainers、OpenAPI、安全、遥测和 Compose 检查；
- 匹配的中英文验证证据；
- 准备维护者验收证据，但不把 P2.2 标记完成。

每个检查点形成一个连贯且已验证的提交。业务实现只在本基线批准后创建 `feature/`
分支；本规划分支与实现分支保持分离。

全表扫描，但不得发布未经测量的规模宣称。

## 13. 发布与回滚

- 不需要迁移或破坏性数据变更；
- `APVERO_KNOWLEDGE_ENABLED=false` 继续作为默认值；
- 禁用 Knowledge 后拒绝新的检索实验室调用；
- 已发布策略和索引版本保持可检查、不可变；
- 回滚使用上一兼容二进制，保留现有数据行；
- 检索实验室在后续验收启用产品界面前仍是非生产实验端点。

## 14. 自我批判与拒绝的捷径

1. 精确向量检索可复现，但对精确标识符和大语料库较弱。P2.2e 不得宣称混合检索、
   语义效果领先或任意规模。
2. 在 SQL `topK` 后应用上下文预算可能返回较少命中。隐藏超额召回会让行为更不透明，
   因此算法版本 1 拒绝这样做。
3. 跳过过大命中可能让后续较小命中进入结果。这能更充分使用显式预算且保持相对顺序，
   并被冻结在算法身份中。
4. 现有 Retention Policy 只有粗粒度开关，不是成熟 DLP 引擎。在有已批准共享遮蔽器
   前，抑制内容比虚假宣称完成遮蔽更安全。
5. 同步查询没有专用持久化查询行。仅为可观测性新增表会违反已批准表清单；本阶段使用
   Governance 与 Trace 证据已足够。
6. 数据库约束宽于公开上下文预算契约。实现必须执行较窄公开范围，不能为方便而接受
   契约漂移。
7. 确定性离线 Embedding 适配器只证明编排，不证明相关性。质量宣称需要后续真实数据集
   评测。
8. 历史可复现与永久删除可能冲突。普通 tombstone 保留旧制品；未来显式删除必须报告
   可复现性被破坏，不能静默改变结果。
9. `NO_EVIDENCE` 有意保守。没有留存证据却返回流畅回答，会破坏 Apvero 的闭环与发布
   不变量。

## 15. 退出声明

只有下述表述能够无保留成立时，P2.2e 才可提交维护者验收：

> 在一个获授权工作区内，Apvero 能发布不可变检索策略，并将其与精确 READY 索引版本
> 配合，执行受治理、确定性、PostgreSQL 作用域限定的余弦查询，返回有界且当前获授权
> 的证据或类型化 NO_EVIDENCE，同时不发生跨工作区泄漏、原始查询留存、隐藏排序行为、
> 重复费用结算或不受支持的质量宣称。

验收只完成 P2.2e。P2.2 必须等 P2.2f 验收加固通过后才可完成。
